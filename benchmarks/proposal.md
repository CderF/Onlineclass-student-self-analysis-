# 计算量评估需求文档

## 一句话定位

实测本系统除模型推理（MediaPipe FaceMesh、YOLO 表情分类）以外的计算开销：每帧耗时、CPU 占用、内存。先找出瓶颈，整理后的结果也要能用于论文。

## 已确认的需求

### 1. 两种口径

| 口径 | 含义 | 本次 |
|---|---|---|
| 「都排除」 | MediaPipe 与 YOLO 的推理都不计入 | 正式实测 |
| 「都包含」 | 两次推理都计入 | 写好脚本，用现有 7 类 `weights/best.pt` 短跑几十帧，只确认能跑通，结果不写入文档；等 #26 的 4 类模型就绪后再正式实测 |

### 2. 「都排除」的实现方式：先缓存再回放

先对测试视频跑一遍模型，把每帧的 MediaPipe 关键点（478 点）和 YOLO 表情概率存成缓存文件。正式测量时不运行模型，只回放缓存，这样下游计算用的是真实数据，模型的开销完全不计入。

### 3. 指标

- 各环节的每帧耗时（ms）
- 进程 CPU 占用率（%）
- 内存占用（MB）

不计算理论 FLOPs。

### 4. 测量范围

| 部分 | 性质 | 内容 |
|---|---|---|
| 每帧处理链路 | 上课时持续发生 | 读帧、EAR / MAR / 头部姿态 / 人脸框等几何计算、画网格与文字、注意力规则（`AttentionAnalyzer`）、转 QPixmap |
| 课程记录 | 上课时持续发生 | `SessionRecorder` 每帧累积，每秒写入并提交 SQLite |
| 界面线程刷新 | 上课时持续发生 | 主线程收到信号后缩放画面，更新分数与状态文字 |
| 课后报告页 | 课后一次性 | 问题时段判定、文字反馈、图表渲染、CSV 导出；用合成的 90 分钟课程记录测量 |

### 5. 输入

- 用户自己录制约 5 分钟的听课视频，代替摄像头，保证每次输入相同、可复现。
- 视频要依次覆盖：正常听课、低头超过 15 秒、闭眼、打哈欠、离开镜头，让注意力规则的各个分支都执行到。录制脚本会给出提示。
- 报告页不用录 90 分钟视频，用合成的课程记录测量。

### 6. 送帧节奏

两种都测：

- **按真实帧率**（30 fps）送帧：测实际使用时的 CPU 和内存；机器跟不上时按实际情况丢帧。
- **尽可能快**地送帧：测单帧耗时和最大吞吐量。

### 7. 测量机器

| 机器 | 说明 |
|---|---|
| MacBook Pro（Apple M4，10 核，16 GB） | 开发机 |
| 用户的 Windows 电脑 | 作为低配机，代表普通学生的电脑 |

脚本必须跨平台，运行时自动记录 CPU 型号、核心数、内存、操作系统、Python 与主要依赖的版本。

### 8. 判定标准

结果文档要针对每台机器、每种口径给出结论：

- **理想线**：每帧处理 ≤ 33 ms，跟得上 30 fps。
- **底线**：帧间隔 < 250 ms。超过这个值时，`attention_rules.py` 的眨眼和哈欠特征会直接变成 0，而且不会报错。原因是同一段闭眼或张嘴中，相邻两帧间隔不能超过 0.25 秒。

### 9. 统计方法

每种条件重复 5 次，去掉开头的预热帧，报告中位数、P95 和最大值。

### 10. 交付物与存放

- 全部放在仓库根目录的 `benchmarks/` 下：测量脚本、中文结果文档、本需求文档。
- 测试视频和关键点 / 概率缓存加入 `.gitignore`，不提交。
- 提交脚本、文档，以及不含画面的测量数据（耗时、CPU、内存的 CSV）。

### 11. 与程序代码的关系

- `app/` 一行都不改。脚本直接导入 `app/` 的模块，按 `CameraThread.run` 的顺序逐步调用并计时。
- 已知代价：以后 `CameraThread.run` 的步骤或顺序改了，`benchmarks/` 的脚本要跟着改。结果文档里要写明这一点。

## 明确不做

- 修改 `app/` 里的程序代码，包括加计时点。
- 性能优化：只在结果文档里列出瓶颈和优化建议，要不要修、怎么修，以后另开 issue。
- 理论 FLOPs 估算。
- 用真实摄像头做正式测量。
- 提交含人脸的视频和关键点缓存（仓库在 GitHub 上是公开的）。
- 用 7 类临时模型出正式的「都包含」结果。
